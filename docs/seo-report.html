Technical SEO Configuration Report

What was configured on this build, page by page — so the implementation can be inspected rather than taken on trust. Every item below is verifiable directly in View Source or against the live files.

What this build is. A self-built reference demo: a static showcase site covering the same technical-SEO surface a WordPress build delivers on the client's own hosting (Cloudflare + SiteGround). It is published so the implementation can be reviewed and stress-tested before any money moves. It is not a WordPress install, and it is not presented as one — the WordPress version is deployed on the client's own hosting, with the admin, database and hosting account handed over.

02 — Architecture

Flat, keyword-bearing, trailing-slash consistent

  • Supporting article cluster under /blog/<slug>/

03 — Structured data

Schema markup on this build

All markup is JSON-LD embedded in the page — inspectable in View Source, no plugin required to render it, and it survives theme changes.

Deliberately absent: Review, AggregateRating and duplicate Organization nodes. Inventing reviews for a demo site would be the fastest way to get a manual action on the client's real domain, and duplicated Organization markup across pages is a common self-inflicted problem — one canonical node referenced by @id is the correct pattern.

04 — Crawl & index

Canonical, hreflang, redirects

Canonical

One self-referencing canonical per URL, absolute and https. No canonical pointing at a different page, no missing tags on paginated or article URLs.

hreflang

This build is single-language, so hreflang is correctly absent. When a second locale is added the pattern is reciprocal tags plus a language switcher: en · x-default · the localised path pair.

Redirects

All 301, never 302, and never chained. www and non-www consolidated to one host, http upgraded to https at the Cloudflare edge and again at origin.

FromToCodePurpose
http://example.com/*https://example.com/*301Protocol consolidation
https://www.example.com/*https://example.com/*301Host consolidation (permanent)
/index.php/301WordPress duplicate entry point
/products/*/capabilities/*301Legacy URL pattern from earlier structure
/?p=123/{post-name}/301WordPress shortlink to permalink
/tag/*, /category/*/blog/301Thin archive consolidation

404s return a real HTTP 404 with a crawlable page (not a soft-404) — on this build the host serves /404.html automatically.

05 — Speed & delivery

What keeps PageSpeed in the green

The single biggest determinant of mobile PageSpeed on a WordPress build is not caching plugins — it is how many render-blocking third-party requests the theme drags in.

  • Zero external requests. No Google Fonts, no jQuery from a CDN, no icon font, no analytics script on this build. System font stack instead.
  • One stylesheet, one script — around 40 KB uncompressed combined, roughly 9 KB over the wire after gzip/brotli.
  • No layout shift. Every element has intrinsic sizing; the SVG logo and icons have explicit dimensions, so CLS stays at 0.
  • Cloudflare in front — edge caching, brotli, HTTP/3, image resizing at the edge rather than on origin.
  • LiteSpeed Cache on origin — page cache, CSS/JS minify and combine, critical CSS generation, WebP conversion, lazy-load below the fold.
  • Fonts self-hosted or system. If a brand font is required it gets self-hosted with font-display: swap and preloaded via <link rel="preload">, never a Google Fonts call.

Target Core Web Vitals

LCP
< 2.0 s on mobile 4G — hero text is server-rendered, no image dependency
INP
< 100 ms — no framework hydration on the front end
CLS
< 0.02 — explicit dimensions everywhere, no injected banners
TTFB
< 400 ms — Cloudflare edge cache hit plus origin page cache
Page weight
< 500 KB total including above-the-fold imagery

Why no analytics here. A demo build should not ship a tracking script that pings a third party on every visit. On the production install GA4 is loaded through the site's own domain with consent handling, deferred until after first interaction.

06 — Verification

How each claim above gets checked

Every line in this report maps to a tool the client can run themselves.

ClaimHow to verify
Unique titles & descriptionsScreaming Frog crawl, free tier covers 500 URLs — check the Title 1 / Meta Description 1 columns for duplicates and length overflows
Canonicals correctScreaming Frog → Canonicals tab; confirm every canonical is self-referencing and absolute
Schema validGoogle Rich Results Test on each URL; Schema.org validator for the non-rich-result types
No soft 404sFetch a nonexistent URL, confirm HTTP 404 in the response headers rather than 200
Sitemap cleanSubmit to GSC → Sitemaps; confirm “Success” and 0 discovered-not-indexed errors
Redirects not chainedcurl -I on each legacy URL — exactly one 301, then a 200
Core Web VitalsPageSpeed Insights for lab data; Search Console Core Web Vitals report for field data (needs ~28 days of traffic)

On indexing timelines. Being honest about this matters: no one controls Google's indexing schedule. GSC verification is immediate, sitemap submission is immediate, but meaningful impressions data typically appears 7–14 days after indexing, and “real” ranking movement needs a month or more. Anyone promising page-one rankings within a fortnight is either buying links or guessing.
